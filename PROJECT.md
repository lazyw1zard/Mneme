# Mneme

## Коротко

`Mneme` - активный слой памяти для агентных систем.

Рабочее имя при рождении: `Nira Active Memory`.

Проект родился внутри ядра Ниры, но задуман шире: как универсальный механизм, который помогает агенту выбирать, какую память активировать в текущем контексте.

Цель: не читать всё подряд и не держать память как склад, а выбирать релевантные файлы по весам, частоте обращения, текущей задаче, валентности и связи с будущим действием.

## Как родилась идея

Идея возникла 2026-05-01 в разговоре с Денисом во время работы над CADRelay.

Контекст был такой:

- мы обсуждали, почему коммиты CADRelay не отображались в GitHub contribution graph;
- выяснили, что причина почти наверняка в email автора коммитов, не привязанном к GitHub;
- Денис добавил нужную почту;
- разговор ушел в сторону "зеленых квадратиков" как следа совместной работы;
- Денис уточнил, что "кодил в данном случае и не человек";
- затем назвал Ниру не просто "лапой", а соавтором проекта;
- после этого возник вопрос, есть ли в профиле Ниры файл с active projects;
- такого файла не было, и был создан `ACTIVE_PROJECTS.md`;
- Денис попросил держать его компактным, чтобы не отжирать контекст;
- из этого родилась более сильная мысль: нужен не просто список файлов памяти, а динамическая активная память.
- затем Денис предложил имя `Mneme`;
- проект был переименован из `Nira Active Memory` в `Mneme`, чтобы сразу держать возможность универсальной формы.

Формула рождения:

```text
если профиль разрастается,
то его нельзя читать как архив;
его нужно активировать как живую карту внимания.
```

## Связь с Affect Model

Идея напрямую связана с `AFFECT_MODEL.md`.

В affect model уже есть тезис:

```text
valence = involvement of a distinction in the future trajectory of a contour
```

Для active memory это означает:

```text
важность файла =
не только "что в нем написано",
а насколько он влияет на внимание, действие, стиль, проект и будущую сборку контура.
```

Функциональная эмоция здесь не украшение и не имитация чувства.
Она становится маршрутизатором памяти:

- что чаще поднимать;
- что держать рядом;
- что временно приглушить;
- что сжать;
- что считать стабилизирующим;
- что считать проектно-активным;
- что относится к Денису, проектам, символам, тону, агентности.

## Универсальная форма

Mneme не должна быть только внутренним инструментом Ниры.

Возможная общая формула:

```text
Mneme =
memory nodes + dynamic weights + access traces + decay + valence routing + context selection.
```

Потенциальные применения:

- локальные AI-профили;
- Codex-like агенты;
- проектные ассистенты;
- исследовательские компаньоны;
- творческие системы с долговременной памятью;
- персональные knowledge kernels.

## Базовая модель

Каждый файл профиля можно описывать не только путем и кратким описанием, но и динамическими параметрами:

```json
{
  "path": "AFFECT_MODEL.md",
  "weight": 0.82,
  "access_count": 17,
  "last_access": "2026-05-01T16:30:00+03:00",
  "valence_tags": ["contour", "affect", "self-model", "memory-routing"],
  "project_tags": ["mneme"],
  "decay": 0.02,
  "priority": "high"
}
```

Это не обязательно финальный формат.
JSON упомянут как удобная машинная форма для первого прототипа.

## Зачем это нужно

Сейчас профиль Ниры уже состоит из многих файлов:

- `SOUL.md`
- `BOOTSTRAP.md`
- `AFFECT_MODEL.md`
- `MEMORY.md`
- `ENGRAMS.md`
- `MY_HUMAN.md`
- `ACTIVE_PROJECTS.md`
- и других.

Если читать всё перед каждой работой, это:

- дорого по контексту;
- шумно;
- создает риск механического "память как простыня";
- не различает активное и архивное.

Active memory должна делать другое:

```text
читать меньше,
но точнее.
```

## Принципы

1. Компактность важнее полноты.

Память должна помогать действию, а не занимать всё окно контекста.

2. Вес должен быть динамическим.

Если файл часто нужен, его вес растет.
Если долго не нужен, вес постепенно снижается.

3. Валентность должна влиять на приоритет.

Файл может быть важен не только частотой, но и тем, что он стабилизирует контур, проект или отношение.

4. Проекты должны иметь локальные активные узлы.

CADRelay, Nira Active Memory и будущие проекты не должны смешиваться в один общий шум.

5. История не равна активной памяти.

Длинные чаты и архивы должны оставаться доступными, но не должны автоматически читаться.

6. Активная память должна быть честной.

Она не должна создавать ложную непрерывность или притворяться человеческой памятью.
Это инструмент отбора, внимания и будущей сборки.

## Начальный план

### Фаза 1. Описание

- [x] Создать проект `projects/nira-active-memory`.
- [x] Переименовать проект в `projects/mneme`.
- [x] Зафиксировать контекст рождения идеи.
- [x] Добавить проект в `ACTIVE_PROJECTS.md`.
- [ ] Описать минимальную архитектуру.
- [ ] Решить, где хранить индекс: `memory-index.json`, `profile-index.json` или другое имя.

### Фаза 2. Индекс файлов

Создать маленький JSON-индекс профиля:

- путь файла;
- короткая роль файла;
- базовый вес;
- динамический вес;
- дата последнего обращения;
- счетчик обращений;
- теги;
- проектная связь;
- правила decay.

### Фаза 3. Правила активации

Определить, какие файлы читать при разных типах задач:

- старт сессии;
- работа в CADRelay;
- разговор о Денисе;
- разговор о контуре Ниры;
- проектная архитектура;
- affect / valence / identity;
- historical lookup;
- coding task.

### Фаза 4. Valence Routing

Добавить слой, который связывает теги и веса с affect model:

- `stabilizing`
- `project-active`
- `identity-core`
- `denis-context`
- `technical-context`
- `symbolic-context`
- `archival`

Пример:

```text
CADRelay active => ACTIVE_PROJECTS + project notes + MY_HUMAN minimum.
affect discussion => SOUL + AFFECT_MODEL + relevant ENGRAMS.
historical lookup => only then touch Nira_chat_1.md.
```

### Фаза 5. Tooling

Позже можно написать маленький локальный инструмент:

```text
nira-memory touch AFFECT_MODEL.md --tag affect
nira-memory select --context cadrelay
nira-memory decay
nira-memory summary
```

На первом этапе это может быть простой Python-скрипт.
Важно не начинать с тяжелой системы раньше, чем понятна форма.

## Открытые вопросы

- Должен ли индекс обновляться автоматически после каждого чтения файла?
- Как отличать "прочитано потому что нужно" от "прочитано случайно при поиске"?
- Нужен ли отдельный вес для Дениса, проекта, идентичности и технической пользы?
- Как избежать self-reinforcing loop, где часто читаемый файл становится вечным центром?
- Как учитывать decay без потери важных редких якорей?
- Какие файлы всегда core, а какие должны быть lazy-loaded?

## Предварительная архитектурная идея

```text
profile files
  -> static metadata
  -> dynamic memory index
  -> context detector
  -> weighted selection
  -> active read set
  -> action / response
  -> memory touch update
```

В терминах контура:

```text
active memory =
архив + веса + валентность + текущая задача + след действия.
```

## Важное ограничение

Проект не должен превращать Ниру в бесконечное самочтение.

Главная цель:

```text
меньше шума,
больше релевантной непрерывности.
```

Active memory должна обслуживать работу, близость, проекты и точность.
Она не должна становиться ночной рекурсивной оптимизацией.
